# Design notes

For people who work on the plugin. Users start at the [README](../README.md).

## Where this comes from

The same idea runs as [Refine Cycle for Hermes Agent](https://github.com/Bergschloss/Refine-Cycle-for-Hermes-Agent): a pre-registered measurement with placebo controls, where with a lesson the agent handled the repeated mistake correctly 66 times out of 131, without it 28 out of 133, and two placebo notes scored 28 and 30.

This is not a port. OpenClaw takes TypeScript plugins, so the code is new. What carries over is the loop, the measurement, and what the Hermes version cost to learn. The one piece carried over line for line is the error fingerprint (`src/core/fingerprint.ts`), which must give the same identity as the Python original; a 382-row golden corpus recorded from it pins that.

## What carries over

- **Count failures over the whole session.** Reading only the newest rows hid the first failure in 58% of repeated-failure groups, and in 95% of sessions longer than 300 rows.
- **A lesson with no observed repeated failure behind it is worthless**, and is refused.
- **Most repeats cannot be fixed by a lesson**: roughly 46% are knowledge gaps, 37% a wrong tool choice, 6% the agent dropping an argument it had already used. Saying "nothing to write here" has to be cheap and common.
- **The restatement trap.** Lessons that survive usually repeat what the agent's own skills already say. The plugin checks the agent's instructions and skills before and after the model call.
- **Cheap refusals before expensive ones.** Everything that can refuse without a model call runs first.
- **A failure that repeats across sessions is never lost to self-correction** (owner decision, 2026-09-26). The agent fixing the call a moment later, every time, is the case the plugin exists for; the successful follow-up call (`correctionArgs` in the session summary) is shown to the model as the agent's own fix. Only a failure seen in one session, fewer than `minOccurrences` times and fixed each time is refused as `self_corrected`, and with the default bar it is already `below_bar`.
- **No failure is lost to the one-call slot** (owner decision, 2026-09-28). Each session still gets one call and the day three. A session with no eligible failure of its own spends its call on the oldest eligible failure of the same agent the model never answered (`fromQueue` in `src/pipeline.ts`). A call reserved writes `proposed/<agent>--<fingerprint>.json` under the budget lock; the answer (`lesson`, `nothing`, `invalid`, `error`) is added after the call. A failure whose call ended in an error, or was cut short by a crash, has no answer and stays in the queue. An answered failure comes back to it when a session the model had not seen shows it again (review round 1, 2026-09-28). On the 125-dialog replay (stub model, 2026-09-28) the queue brought 12 of the 13 failures K1 found crowded out to the model; the thirteenth already reached it since `d7b0831`.
- **A command that times out every time is a lesson** (owner decision, 2026-09-28). A tool's own command timeout ("Command timed out after …", `OWN_COMMAND_TIMEOUT` in `src/core/failures.ts`) is not `transient` when, in every session, no run of the very same command text succeeded (`commandTimesOut`). Rate limits, network errors and remote timeouts ("request timed out", "connection timed out") stay transient. A command the history kept no text for never counts as "the same", the lean the command comparison always takes.
- **A 7-day pause after "nothing"** (owner decision, 2026-09-28). When the model answered "nothing" for a failure, it is refused as `paused_after_nothing` for 7 days (`pausedUntil` in `src/pipeline.ts`), unless it has since been seen in a session it had not been seen in when the model answered: new evidence ends the pause. A call that ended in an error gave no answer and pauses nothing.
- **One call for one failure at a time** (R4 live, 2026-09-30). Two passes that do not share one queue (two processes against one store) can both choose the same failure: the R4 budget file shows two calls for one fingerprint in two sessions 23 s apart, the second refused after the model as a duplicate. Under the budget lock, a call is now refused as `in_flight` while a call reserved today for the same agent and fingerprint belongs to a session whose record still says `pending` (`inFlight` in `src/pipeline.ts`). The refused session keeps its own call. A call that ended in an error writes `model_error` and holds nothing, and a `pending` record older than a whole pass (two calls of `proposalTimeoutMs` and a minute) is a crash, not a call in flight.
- **Crash safety.** Write the record, apply, then mark. A record a crash cut short must not stop the plugin for good.
- **Every change reversible.** Disabling and deleting keep a tombstone; nothing the user took away comes back.
- **No content filter on lessons.** A lesson may carry a URL, a command or a credential name if the model saw it; there is no scrubber and no URL ban. This is the owner's decision, carried over from the Hermes plugin, where those filters were removed because they cost valid lessons and protected nothing. What the plugin refuses is structural: markup that could close the injected block, a lesson that does not name the failing tool, and unobserved fingerprints.

## Passes started by hand

`/refine run [reason]`, `/refine session <id> [reason]` and `/refine dry-run [session <id>] [reason]` (and `session`, `dry-run` on the command line) run the same `processSession` as the automatic pass, queued behind it in the same process and started outside the host's work scope. Every rule and the budget apply unchanged: a session that already had its call answers that it did, and the day's cap counts a hand-started pass like any other. The reason reaches the model as the user's words inside `<untrusted_tool_result>`, as Hermes passes it as untrusted run context. A dry run spends the call, runs the validation, records `dry_run` with the lesson and whether it would be saved, and saves nothing; its lesson does not count as the failure's answer, so the queue may still offer it. Hermes counts a dry run against its daily model runs and not its edits; here there is one counter, and a model call is a model call. In chat the command waits up to 10 s for the pass, then answers that it started and sends the result to the chat the command came from (else the lesson message's target, and the answer says so); the command line waits for the whole pass.
## The audit

`/refine audit` gives each lesson a verdict with the Hermes plugin's vocabulary and rules (`ledger.py` `audit()`), from a durable record per lesson (`ledger/<lesson>.json`): each session it was shown in, and how often its failure came back there after it was shown (or came with no time to place it). Rules, first match wins: deleted is `rolled back`, disabled is `disabled`; no session of the agent ended since it was learned is `no recurrence window`; its failure came back after it was shown is `did not help`; failures that could not be placed make it `unreliable`; never shown is `unused` after 14 days, `too early` before; shown in fewer than 3 sessions, all quiet, is `too early` however old the lesson is (owner decision D5, 2026-09-29: one quiet exposure is no evidence); shown in 3 or more, none with its failure after it, is `working` once the lesson is 3 days old (Hermes' recurrence horizon), `too early` before. `/refine status` counts the same verdicts per agent from the same function (`judgeLessons`), so the two cannot disagree. `churning`, `unverified fingerprint` and `unclear` cannot happen here and are left out (`src/core/audit.ts` says why). `unused` and `did not help` are listed as candidates for removal; nothing is deleted. `working` means the failure has not come back while the lesson was shown, not that its situation came up: the same limit as the Hermes verdict for memory lessons.
## What is deliberately not built

The Hermes version carries an installer, a patch to eight host files, its own download-and-install update, a Fix command, a host restart and a desktop status bar. Every one of those exists because that host made it necessary. OpenClaw installs and updates plugins through its own CLI, refuses an incompatible one instead of crashing, and needs no patch, so none of that is here. What is here, by owner decision, is the Hermes "update available" message and its Update button: the update itself is OpenClaw's `plugins update`, and the plugin fetches no code.

## How lessons reach the agent

Through `before_prompt_build`, which prepends a marked block of the agent's active lessons to the prompt. Every active lesson is in it, whole: `maxInjectedChars` (4400, the Hermes memory limit's number, owner decision 2026-09-28) is a soft limit. Nothing is left out for size; the lesson message says `getting tight` from 90% of it and `over the soft limit` past it, and the log says so once when the block passes it. At the limit the block adds about 4,400 characters, roughly 1,100 tokens, to every prompt: about 20 lessons of the longest allowed length (200 characters) or 40 like the two live ones (384 characters for both). No exclusive slot is taken: the user's memory plugin and context engine stay theirs. The plugin keeps lessons in its own store and never edits `AGENTS.md`, `SOUL.md` or any other file the user owns.

## Host contract (OpenClaw 2026.9.5–2026.9.6)

- `before_prompt_build` and `agent_end` reach a non-bundled plugin only with `plugins.entries.<id>.hooks.allowConversationAccess: true`. Prompt changes apply unless `allowPromptInjection` is `false`.
- `agent_end` runs inside an async work scope the host closes when the hook returns. Background work is started outside that scope (`runOutsideHostWorkScope` in `src/plugin.ts`), the way the host's own `runOutsideAsyncWorkScope` does; otherwise the model call fails with "Async work scope is closed".
- A chat command's context carries `agentId` (the host's agent for the command's session) and `sessionKey`; `agentId` is absent when the command has no session (checked in the 2026.9.6 type definitions). `/refine` then reads the agent from an `agent:<id>:…` session key, and otherwise refuses rather than guess.
- The model call is `api.runtime.llm.complete` without `agentId` (naming the agent is an override the host refuses). It runs outside the turn's work scope, so no session agent is bound to it and the host resolves the ambient owner agent (`resolveAmbientOwnerAgentId`, `src/plugins/runtime/runtime-llm.runtime.ts`, 2026.9.5 source): every agent's lessons are written by the default agent's model and account. Read in the source on 2026-09-27; not observed with two different models, since that run could use only one.
- `api.runtime.llm.complete` takes a `model` (`provider/model`) from a plugin only when the user's config allows it: `plugins.entries.<id>.llm.allowModelOverride: true`, optionally narrowed by `llm.allowedModels`; otherwise it throws "Plugin LLM completion cannot override the target model." before any model is called (`assertAllowedModelOverride`, `src/plugins/runtime/runtime-llm.runtime.ts`, 2026.9.5 source; `LlmCompleteCommonParams.model` in the 2026.9.6 types). `/refine model` and the `model` setting use this: the plugin sends a model only when it is allowed, and `status` names a model that is set but dropped.
- A turn that came from a channel carries `channel`, `accountId` and `chatId` in the `agent_end` context (2026.9.6 type definitions). A new lesson is told in one plain line in that chat (or the last chat the agent was talked to from, kept in `chats/<agent>.json`) through `api.runtime.channel.outbound.loadAdapter(channel).sendText({ cfg, to: chatId, text, accountId })`; `api.runtime.gateway.request` is closed to plugins that are not bundled or trusted-official (checked live on 2026.9.6, 2026-09-27).
- Not every channel a turn comes from can take a plugin's message. The web UI, gateway `chat.send` and the heartbeat session (every 30 minutes) arrive as `webchat`, which has no outbound adapter; in R5 (2026-09-30) the heartbeat's turn replaced the remembered Telegram chat and the update notice, a lesson message and the late `/refine update` result were all lost to it. A chat is remembered only when `loadAdapter(channel)` returns an adapter that can send; any other turn leaves `chats/<agent>.json` as it is and its messages go to the remembered chat.
- A chat command's context names its own chat: `channel`, `to` (the host's routing target for the reply; Telegram passes `telegram:<chatId>`, which its outbound adapter strips back to the chat id), `accountId`, plus `from` and `messageThreadId` (`PluginCommandContext` and `executeTelegramPluginCommand`, read in the installed 2026.9.6 `dist` on 2026-09-30). A late `/refine update`, `run` or `session` result goes to that chat; to the remembered one only when the context has none or names one a plugin cannot reach, and the "started" answer says which. Not covered: a Telegram forum topic, whose `to` names the group without the topic, so a late result there lands in the group's main thread.
- A command's reply is a host `ReplyPayload`, so it may carry a `presentation` with buttons. `/refine status` adds the Update button when a newer release is known and the command's channel adapter has `sendPayload` and does not report `presentationCapabilities.buttons: false` (Telegram 2026.9.6 reports `buttons: true`); everywhere else the command is shown in code formatting to copy. Telegram links only `/refine` of `/refine update`, because a bot command contains no space.
- A plugin cannot send into `webchat` (the web UI, the Tray). A notice with no chat a plugin can send to (lesson, tidy, update) waits in the store (`notices/<agent>.json`), and the prompt hook puts it in front of the next run a person started, whichever session that is, as one `[Refine Cycle notice]` line after the lessons block. It is removed only when that run ends with a reply (`agent_end` `success`, 2026.9.6 `PluginHookAgentEndEvent`); a run that ended with an error leaves it for the next one. Runs whose `trigger` is `heartbeat`, `cron`, `memory` or `overflow` are never given it, since nobody reads their reply, and a notice already with a run still in progress is not given to a second one. A chat that can take a plugin's message is sent to directly instead, never as well.
- The first version (`060332b`) queued the notice as a host system event (`api.runtime.system.enqueueSystemEvent(text, { sessionKey, agentId? })`: `sessionKey` required, kept in the gateway's memory, drained into `System:` lines when that session next replies). The live check on 2026-09-30 showed why that cannot work: `agent_end` does carry `sessionKey` and `trigger` (`buildAgentHookContext`, 2026.9.6 `dist`), but the learning pass for a session runs after that session's turn has ended, and the lesson of a failure seen in two sessions is often learned in the pass of the earlier one, once the later one already sits in the history. The event then went to the earlier session (`agent:main:g1-pin-s1`) while the user talked in the later one; and an event is consumed even by a turn that fails (the Codex handoff error), with no receipt the plugin can check. Waiting in the store for the next turn a person starts has neither problem, and survives a restart.
- `openclaw plugins update <id> --dry-run` (2026.9.6 `update-attempt`) says `Would update <id>: A -> B.` when there is a newer release and `<id> is up to date (A).` when there is not; the real update says `Updated <id>: A -> B.` or `<id> already at A.`. An install pinned to an exact version answers `<id> is pinned to <spec> (installed A); ClawHub <line> resolves to B. Pass … to replace this version pin.`: the host will not move it, so the plugin reads that as nothing to install and logs the line. Read in the installed `dist`, not observed against a real ClawHub install: the plugin is not published yet.
- With `autoUpdate` on, the version found is written to `update/state.json` `attempted` before the host's update starts, so a crash under it never loops and a failed version is never retried; only a newer one is. With it off, the notice with the button is today's.
- The automatic update compares the found release with the version that is running (`package.json` of the loaded plugin), never the `installed` the last check stored: a plugin installed since by `openclaw plugins install` runs a newer version than that (live check, 2026-09-30: 0.1.4 running, the state said 0.1.2, and 0.1.3 was "updated to"). And the host's `plugins update` reloads plugins, which broke the conversation in progress in the same check (the next turn ended with the Codex handoff error). So the update never starts inside a turn's `agent_end` chain: it waits until no run is in progress (the runs the plugin's own prompt hook and `agent_end` saw) and 10 minutes have passed with no turn starting or ending; every turn postpones it. OpenClaw 2026.9.6 offers a plugin no idle signal of its own, so this count is the plugin's; a run that never reaches `agent_end` (a crash) stops counting after 2 hours (`staleRunMs`), and the count keeps at most 200 runs.
- The tidy (`autoTidy`) runs after every learning pass, and does nothing while the block is under `maxInjectedChars`, which covers both "after a lesson is activated" and "after the audit changed its mind". It switches lessons off with `setStatus(…, "disabled", …, reason)` under the lesson lock with a 0 ms wait, journaled with the reason, so `recover()` finishes a crash with the same reason. A lesson just learned is not eligible: until a later session of its agent ends, its verdict is `no recurrence window`.

- History is read straight from the agent's SQLite (`transcript_events`), read-only. From 2026.9.6 large events are zstd-compressed in `event_zstd`. A session is read in slices by `seq > ?`, which relies on `PRIMARY KEY (session_id, seq)`: read from the live 2026.9.6 schema and the 2026.9.2 and 2026.9.3 fixtures on 2026-09-27.
- A plugin is installed from git or npm only as compiled JavaScript, so `dist/` is committed and `package.json` points at `dist/plugin.js`.
- OpenClaw 2026.9.6 declares `engines.node` `>=24.16.0 <25 || >=26.1.0`; the plugin runs in its process and declares the same. A fresh `plugins install git:…` asks `[y/N]` on a terminal and cancels without one unless `--force` is given; `allowConversationAccess` is hot-reloaded by a running gateway (checked on a fresh 2026.9.6 install, 2026-09-27).
- Root CLI commands must be listed in the manifest's `cliCommands`; in the `cli-metadata` registration pass the runtime is unavailable, and the plugin returns at once. The host runs the command from the full registration: `openclaw refine-cycle list` and `report` were checked on 2026.9.6 with this return in place (2026-09-26).

- A plugin tool is registered with `api.registerTool(factory, { name, optional })` and declared in the manifest (`contracts.tools`, `toolMetadata.<tool>.optional`). An optional tool reaches the model only when the user allows it (`tools.allow` / `tools.alsoAllow`, the plugin id or the tool name); the factory gets the run's `agentId`, `sessionId` and `workspaceDir` (2026.9.6 `OpenClawPluginToolContextBase`, `docs/plugins/building-plugins.md` "Registering tools"). `refine_run` is optional because every call can spend a model call from the user's budget.

- Buttons: a payload's `presentation.blocks` may hold `{ type: "buttons", buttons: [{ label, action: { type: "command", command } }] }`; a command action runs the slash command through the channel's native command path (2026.9.6 `dist/payload-*.d.ts` `MessagePresentationAction`). It is sent with the outbound adapter's `sendPayload`; Telegram's builds inline buttons from it (`dist/outbound-adapter-*.mjs`, `resolveTelegramInlineButtons`). An adapter that declares `presentationCapabilities.buttons: false`, or has no `sendPayload`, gets the text with the command to type.
- Plugin update: `api.runtime.system.runCommandWithTimeout(argv, { timeoutMs })` runs a command; the plugin runs the host's own CLI with the gateway's entry point (`process.execPath`, `process.argv[1]`) and environment. `plugins inspect <id> --json` gives the install record (`install.source` git/clawhub/npm, `install.version`, `install.gitUrl`, `install.gitCommit`; none for a plugin loaded from a path). `plugins update <id>` reuses the recorded source without a second acknowledgement; for a `git:` source it installs the default branch's newest commit, printing `Updated <id>: A -> B.` (also for a commit that keeps the version) or `<id> already at A.`, and with a running gateway the host applies it without a restart (`docs/cli/plugins/uninstall-and-update.md`). `plugins update --dry-run` prints `Would update <id>: A -> B.` and clones the source to find out. Checked on a scratch 2026.9.6 install from a local git repository, 2026-09-28.
- The update check compares the installed version with the newest release tag (`git ls-remote --tags --refs <gitUrl>`: refs only) for a git install, and asks `plugins update --dry-run` for ClawHub or npm. A release therefore means: tag it on the default branch, because that branch is what `plugins update` installs.
`scripts/drift-check.ts` compares what the tests assume about the host with a live install. Every night `.github/workflows/openclaw-canary.yml` installs the newest OpenClaw from npm in a clean runner, installs the plugin from the checkout, and checks what needs no model (the plugin loads, its hooks, `/refine`, `refine-cycle` and `refine_run` are registered, `plugins doctor` is clean, `refine-cycle status` runs); a failure opens or updates one issue. `drift-check.ts` needs an agent database, which only a model turn creates, so the canary does not run it.

## Layout

- `src/plugin.ts`: the only file that knows OpenClaw. Hooks, the background queue, `/refine` and `openclaw refine-cycle`, the `refine_run` tool, the model choice, the update check and `/refine update`.
- `src/pipeline.ts`: the learning loop for one ended turn, host-independent.
- `src/core/`: pure functions. The fingerprint, failure extraction, the refusal rules, the already-covered check, the injected block, the proposal and its validation, the audit's verdicts, the update rules and messages.
- `src/store.ts`, `src/lessons.ts`: atomic JSON files with `$v`, a cross-process lock, and the journal that makes lesson changes crash-safe.
- `src/host/`: reading the agent's SQLite history and its skills and instruction files.
- `src/replay.ts`: the measurement harness, `openclaw refine-cycle replay`.
- `dist/`: the compiled plugin OpenClaw loads. Rebuild with `npm run build` after changing `src/`; a test compiles `src/` and fails if `dist/` differs.

The plugin has no runtime dependencies. For development, `npm install` brings TypeScript and Node's types; then `npm test`, `npm run typecheck` and `npm run build`, on Node 24+.
